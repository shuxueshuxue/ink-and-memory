内容讲的是 **Notion CLI 如何同时为人类开发者和 AI Agent 设计命令行工具**。核心总结如下：

## 核心主题

Notion CLI 的设计目标不是单纯做一个“能用的命令行工具”，而是做一个：

**人能逐步理解，Agent 能稳定调用，脚本能可靠解析的现代 CLI。**

## 四个设计原则

### 1. 渐进式披露

CLI 不应该一开始把所有命令全部展示出来。

它采用类似树状结构：

```bash
ntn help
ntn workers help
ntn workers sync help
```

用户或 Agent 可以一层层往下探索。这样既不会让人被大量命令淹没，也不会浪费 Agent 的上下文窗口。

重点是：

**先展示顶层命名空间，再按需展开子命令。**

---

### 2. 错误信息必须可行动

错误不能只是冷冰冰地报错。

比如命令缺少参数时，CLI 会直接提示需要什么 key，用户几乎可以复制后继续执行。

另一个例子是 API 返回 404。程序上是“找不到”，但 CLI 会进一步解释：很可能是这个数据源没有共享给 CLI key。

重点是：

**错误信息要告诉用户下一步该做什么，而不是只告诉用户哪里错了。**

---

### 3. 区分 stdout 和 stderr

CLI 输出里有两类东西：

一类是真正的数据，比如 JSON，应该走 `stdout`。

另一类是辅助信息、请求日志、verbose 信息，应该走 `stderr`。

这样脚本才能安全处理数据：

```bash
ntn workers list --json | jq
```

如果辅助信息也混进 stdout，就会污染 JSON，导致脚本解析失败。

重点是：

**数据归数据，提示归提示。不要把所有东西都 print 到一个出口。**

---

### 4. 同时支持交互式和非交互式模式

人类开发者使用 CLI 时，可以接受交互式 prompt。

但 Agent 或脚本不能停下来选择选项。

所以 Notion CLI 会检测是否有 TTY：

有 TTY：给人类用户展示交互式登录流程。

无 TTY：切换成适合脚本/Agent 的流程，例如输出登录 URL，让用户打开，然后再用另一个命令等待认证完成。

重点是：

**同一个 CLI，要根据使用者是人还是 Agent，自动切换行为。**

## 一句话总结

这份内容的价值在于：它把现代 CLI 的设计从“命令能跑”提升到“人类、脚本、Agent 都能稳定使用”。

最值得记住的是这四句话：

```text
命令结构要能逐层探索。
错误信息要能指导下一步。
真实数据走 stdout，辅助信息走 stderr。
交互式给人，非交互式给脚本和 Agent。
```

做 Ink & Memory、Agent runtime、Claude Code 类工具也很有参考价值：**面向 Agent 的工具，不是把人类 CLI 原样塞给模型，而是要控制信息量、结构化输出、明确失败恢复路径。**
